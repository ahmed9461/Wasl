## ما تم إنجازه وظيفيًا

### الدفتر والحسابات

- أشخاص وحسابات متعددة للشخص نفسه.
- اتجاهان: لي عند الناس / عليّ للناس.
- YER / SAR / USD مع Minor Units صحيحة.
- Ledger append-only.
- دفعات جزئية ونهائية.
- عكس دفعة موثق بدل حذف التاريخ.
- Idempotency للعمليات المالية الحساسة.

### الاستحقاق والمتابعة

- تاريخ استحقاق اختياري وتعديله وإلغاؤه مع Audit.
- متابعة ذكية: قبل الموعد، يوم الموعد، بعده، ثم متابعة دورية.
- WorkManager + Recovery.
- منبه قوي اختياري عبر AlarmManager/Exact Alarm عند الحاجة.
- إجراءات آمنة من الإشعار: دفع جزء، تم السداد، ذكرني لاحقًا، فتح الحساب.
- تذكيرات متابعة عامة مستقلة عن تاريخ الاستحقاق.

### الوعود والأقساط

- وعود سداد مستقلة عن Ledger مع تاريخ وحالات محفوظة.
- خطط أقساط مستقلة عن Ledger مع Revision history.
- تقدم الأقساط مشتق من الدفعات الحقيقية.
- Today يجمع الاستحقاقات والوعود والأقساط دون خلط نماذج البيانات.

### البحث

- البحث الأساسي Reactive داخل Room.
- البحث المتقدم منفذ بالفعل، بما فيه العمليات/المستندات/المبالغ/التواريخ والفلاتر اللازمة.
- اختبارات Advanced Search وAdaptive Search موجودة؛ لذلك **البحث المتقدم ليس مرحلة متبقية** رغم أن `HANDOFF.md` القديم كان يسجله كمرشح تالٍ.

### المستندات PDF

- إيصال سداد.
- إيصال دين.
- كشف حساب كامل متعدد الصفحات.
- Snapshot تاريخي ثابت.
- SHA-256 وسلامة الملف وعدد الصفحات وحالة التوليد.
- فتح ومشاركة عبر FileProvider/مسار الملف الآمن.
- CI يفحص ملفات PDF الحقيقية.

### النسخ الاحتياطي والأمان

- Backup/Restore مشفر بكلمة مرور.
- تحقق من بنية النسخة والملفات وSHA-256 قبل الاستعادة.
- Rollback عند فشل الاستعادة.
- App Lock عبر BiometricPrompt / Device Credential.
- `FLAG_SECURE` وسياسات خصوصية الإشعارات.

## أين كان آخر توقف فعلي؟

السجل القديم في `HANDOFF.md` توقف عند رأس أقدم قبل اكتمال البحث المتقدم. بعد ذلك تم تنفيذ البحث المتقدم والتكيفي، ثم استمرت مراحل المستندات والتذكيرات والإجراءات الآمنة والإصلاحات الحالية.

بالتالي نقطة الانطلاق الصحيحة الآن ليست "البحث المتقدم"؛ بل المراحل التالية أدناه.

## المراحل المتبقية — ترتيب التنفيذ

### المرحلة A — «طالبني» / المطالبات

مرجعها قسم «طالبني» في المواصفة الأساسية.

المطلوب:
- تسجيل أن الطرف الآخر طالب المستخدم بالسداد لحساب من نوع `PAYABLE`.
- حفظ الحدث تاريخيًا بدل مجرد Boolean عابر.
- خيارات متابعة: اليوم، غدًا، عند الراتب، تاريخ مخصص.
- إظهار الأولوية في Today.
- ربط التذكير الناتج بالمطالبة دون إنشاء عملية مالية أو تغيير Ledger.
- اختبارات Repository/Room/ViewModel/UI وعدم كسر النسخ الاحتياطي.

### المرحلة B — المرفقات وخزنة الإثباتات

المطلوب:
- صور / PDF / ملفات مرتبطة بالدين، ومعرّف عملية اختياري عند ارتباطها بدفعة.
- metadata: النوع، الاسم، الحجم، SHA-256، وقت الإضافة.
- تخزين داخلي خاص بالتطبيق؛ لا مسارات عامة غير مضبوطة.
- FileProvider للعرض/المشاركة عند فعل صريح.
- عدم اعتبار الملف إثباتًا قانونيًا تلقائيًا في النصوص.
- إدخال الملفات ضمن Backup/Restore والتحقق من hash والـpath traversal.
- اختبارات تلف/فقد الملف والاستعادة.

### المرحلة C — صفحة الشخص الكاملة

المطلوب:
- تجميع عدة حسابات للشخص نفسه.
- بيانات اتصال وصورة اختيارية.
- ما له / ما عليه حسب العملة.
- الديون المفتوحة والمغلقة.
- Timeline موحد عبر الديون والدفعات والوعود والمطالبات والمستندات والمرفقات.
- عدم جمع عملات مختلفة في إجمالي واحد مضلل.

### المرحلة D — الرسائل الجاهزة والمشاركة

المطلوب:
- قوالب لطيف / عادي / رسمي.
- نسخ ومشاركة وفتح تطبيق مراسلة متاح.
- لا إرسال تلقائي دون فعل المستخدم.
- لاحقًا يمكن إضافة صياغة AI اختيارية.

### المرحلة E — الوصول والتكيف مع الشاشات

المطلوب:
- توسيع اختبارات Compact/Medium/Expanded.
- Font scale أكبر.
- TalkBack semantics وترتيب التركيز.
- Touch targets والنصوص الديناميكية.
- مراجعة RTL/LTR للأرقام والأموال والتواريخ.

### المرحلة F — الإحصاءات الموضوعية

- عدد الديون المسددة.
- متوسط مدة السداد/التأخير.
- عدد الوعود المنفذة وغير المنفذة.
- بيانات موضوعية فقط، دون تصنيفات شخصية مثل "موثوق/سيئ".

### المرحلة G — ميزات المرحلة اللاحقة

- الإدخال الطبيعي للنص مع Preview إلزامي قبل الحفظ.
- الإدخال الصوتي → نص → تحليل → Preview → تأكيد.
- المصاريف/الديون الجماعية.
- أي AI يبقى مساعدًا ولا ينفذ كتابة مالية حساسة بدون تأكيد.

### المرحلة H — جاهزية الإصدار والتوزيع

- Release signing منفصل عن debug.
- حماية مفاتيح التوقيع في GitHub Secrets/بيئة الإصدار.
- Release build + lint/tests/instrumentation.
- versioning وchangelog.
- سياسة الخصوصية وبيانات المتجر عند الحاجة.
- APK/AAB حسب قناة التوزيع النهائية.

## سياسة الجودة لكل مرحلة

لا تعتبر أي مرحلة مكتملة بمجرد نجاح compile. يجب أن تمر، بحسب ما يمسها، عبر:

1. Unit tests للمنطق.
2. Room/instrumentation عند وجود تخزين أو migration.
3. Compose/UI tests للمسار المرئي.
4. Lint.
5. Debug/Release build المناسب.
6. اختبار استعادة/Idempotency عند وجود scheduling أو عمليات حساسة.
7. اختبار Backup/Restore عند إضافة بيانات دائمة جديدة.
8. تحديث `CURRENT_STATUS.md` و`HANDOFF.md` و`CHANGELOG.md` والقرارات المعمارية عند الحاجة.

## قاعدة التصميم الحالية

تُنفذ المزايا والثبات أولًا، ثم تتم جولة إعادة تصميم شاملة للواجهات بعد اكتمال المراحل الوظيفية الأساسية. أثناء التطوير الحالي يجب فقط منع العيوب الوظيفية أو التداخلات الواضحة في الواجهة وعدم بناء تصميم مؤقت يعقّد إعادة التصميم لاحقًا.
